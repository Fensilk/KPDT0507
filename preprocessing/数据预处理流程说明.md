## 1. 整体概览：我们在做什么

想象一下这个场景：摄像头持续监控一个有老人活动的房间。系统需要**实时地**判断：

- 老人有没有**正在跌倒**？（fall —— 一个瞬间动作）
- 老人是不是**已经倒在地上**？（fallen —— 一个持续状态）

这两个问题很不一样：

| | fall | fallen |
|---|---|---|
| 性质 | 瞬时事件 | 持续状态 |
| 持续时长 | ~1秒 | 可能几分钟 |
| 报警紧迫度 | 高（及时发现） | 极高（医疗黄金时间） |
| 训练目标 | 检测动作发生的瞬间 | 识别倒地后的静止状态 |

我们的目标是训练一个**时间线分割模型**（Timeline Segmentation Model）：输入一段视频，输出每一小段时间片段是什么动作。它的输出看起来像这样：

```
walking → walking → fall → fallen → fallen
   0s       1s       2s      3s       4s
```

Step 1-4 做的事情就是把原始的「视频 + 时间段标注」转换成「特征向量序列 + 标签序列」——**让模型能直接吃进去训练**。

处理完成后，一个视频从：

```
81帧 .mp4 + "2.0s-3.1s 发生 fall" 这样的标注
```

变成了：

```python
features:     [5, 512]     # 5个时间片，每个512维特征向量
labels:       [5]          # 每个时间片的动作类别
fall_label:   [5]          # 是不是"正在跌"
fallen_label: [5]          # 是不是"已经倒了"
```

## 2. 数据来源：OmniFall 数据集

**数据集全称**：OmniFall（ominifall）  
**来源**：HuggingFace — `simplexsigil2/omnifall`  
**我们使用的子集**：OF-Syn（OF-Synthetic），即使用光流引导合成的虚拟视频  

### 为什么选 OmniFall？

市面上大多数跌倒检测数据集只给「fall / non-fall」的标签，而 OmniFall 的特殊之处在于：

1. **统一的时间线标注体系** —— 给每个时间段标上动作类别，而不是只标整个视频
2. **强调 fallen 状态** —— 不仅关注跌倒瞬间，更关注跌倒后的倒地静止状态（这对医疗报警更重要）
3. **16 类细粒度动作** —— 不只是 "fall or not"，还有 walk、lying、sitting、crawl 等

### 数据规模

| 项目 | 数量 |
|------|------|
| 视频总数 | **12,000** |
| 每视频帧数 | **81 帧**（~5.06秒 @ 16 FPS） |
| 原始动作标注段 | ~160,000 个时间段标注 |
| 视频编码 | AV1（高效压缩） |
| 存储格式 | 单个 9.7 GB tar 归档文件 |

### 16 类动作标签

```
0: walk         4: sitting       8: standing     12: squat_down
1: fall         5: lie_down      9: other        13: squatting
2: fallen       6: lying        10: kneel_down   14: crawl
3: sit_down     7: stand_up     11: kneeling     15: jump
```

### 数据集划分

| 划分 | 视频数 | 占比 |
|------|--------|------|
| train | 9,600 | 80% |
| val | 1,200 | 10% |
| test | 1,200 | 10% |

## 3. Step 1 — 加载与验证原始数据

**脚本**：[`step1_load_ofsyn.py`](step1_load_ofsyn.py)

### 做什么？

第一步不训练模型，只做一件事：**确认数据能读出来，没有损坏，标签能看懂**。

### 具体操作

```
1. 读取 labels/of-syn.csv     → 拿到每个视频的时间段标注
2. 读取 splits/syn/random/    → 拿到 train/val/test 划分
3. 读取 videos/metadata.csv   → 验证路径一致性
4. 检查 tar 归档文件是否存在    → 确认视频文件齐全
5. 打印几个完整的时间线示例     → 人眼确认标注合理
```

### 验证结果

| 检查项 | 结果 |
|--------|------|
| 标注段（temporal segments） | ~160,000 条 |
| 唯一视频数 | 12,000 |
| 标注覆盖 split 比例 | 100% |
| 元数据交叉验证 | 路径完全匹配 |
| 视频归档 | 存在，9.7 GB |

### 关键理解

原始标注是**时间段级别**的，不是帧级别的。一条标注长这样：

```
路径: fall/fall_ch_001
[0.00s - 2.06s]  standing       # 站着
[2.06s - 2.94s]  fall           # 跌倒过程
[2.94s - 5.06s]  fallen         # 倒在地上
```

这就是时间线标注：同一段视频被标记为连续的"阶段"，每个阶段有开始时间、结束时间和动作类别。

## 4. Step 2 — 从时间段标注到 Clip 序列

**脚本**：[`step2_clip_segmentation.py`](step2_clip_segmentation.py)

### 为什么要做这一步？

Step 1 拿到的标注是**长短不一的时间段**（有的 0.5 秒，有的 3 秒），而模型训练需要**等长的输入单元**。

我们需要把视频切成固定大小的「片」（clip），然后给每个 clip 打上标签。

### 切分方案

```
每视频 81 帧，FPS = 16
每 clip = 16 帧 = 1.0 秒
每视频 = 5 个 clip (5 × 16 = 80 帧，最后 1 帧舍去)

┌─────────────────────────────────────────────┐
│ 81 帧 = ~5.06 秒                            │
├──────┬──────┬──────┬──────┬──────┬──┤
│ clip0│ clip1│ clip2│ clip3│ clip4│  │  最后一帧舍去
│ 16帧 │ 16帧 │ 16帧 │ 16帧 │ 16帧 │  │
│ 1.0s │ 1.0s │ 1.0s │ 1.0s │ 1.0s │  │
└──────┴──────┴──────┴──────┴──────┴──┘
```

### 标签分配方法：中心时间对齐

每个 clip 取它的**中心时间点**，看这个时间点落在原始标注的哪个时间段内，就分配那个时间段对应的标签。

```
原始标注:
  [0.0s ----- 2.0s standing] [2.0s ----- 3.1s fall] [3.1s ----- 5.0s fallen]

Clip 中心时间:
  clip0 中心: 0.5s  → 在 standing 段 → 标签 = standing
  clip1 中心: 1.5s  → 在 standing 段 → 标签 = standing
  clip2 中心: 2.5s  → 在 fall 段     → 标签 = fall
  clip3 中心: 3.5s  → 在 fallen 段   → 标签 = fallen
  clip4 中心: 4.5s  → 在 fallen 段   → 标签 = fallen

结果序列: standing → standing → fall → fallen → fallen
```

### 输出：`data/ofsyn_clips.csv`

| 列名 | 说明 |
|------|------|
| `path` | 视频路径 |
| `split` | train / val / test |
| `clip_idx` | clip 序号 (0-4) |
| `start_frame` / `end_frame` | 起止帧号 |
| `start_time` / `end_time` / `center_time` | 起止时间 / 中心时间 |
| `label` | 16 类动作标签 (0-15) |
| `label_name` | 标签可读名称 |

**统计**：共 60,000 个 clip（12,000 视频 × 5 clip），0 个 clip 无法匹配标签。

## 5. Step 3 — 生成双分支二值标签

**脚本**：[`step3_binary_labels.py`](step3_binary_labels.py)

### 为什么要做这一步？

Step 2 的输出是每个 clip 的 16 类动作标签。但对于跌倒检测这个具体任务，我们实际上关心两个**二分类问题**：

1. **fall 分支**：这个 clip 里有人在跌倒吗？
2. **fallen 分支**：这个 clip 里有人正倒在地上吗？

### 二值标签生成规则（非常直接）

```python
fall_label   = 1  当 label == 1 (fall)    否则 0
fallen_label = 1  当 label == 2 (fallen)  否则 0
```

### 实例

一个视频的 clip 标签序列为 `standing → standing → fall → fallen → fallen`：

```
clip 序号:       0          1          2          3          4
16类标签:    standing  standing     fall    fallen    fallen
label 值:        8          8         1         2         2
               ↓          ↓         ↓         ↓         ↓
fall_label:      0          0         1         0         0    ← 只有 clip2 是"跌倒"
fallen_label:    0          0         0         1         1    ← clip3-4 是"倒地状态"
```

### 在 `data/ofsyn_clips.csv` 中新增两列

| ... | label | label_name | fall_label | fallen_label |
|-----|-------|------------|------------|--------------|
| ... | 8 | standing | 0 | 0 |
| ... | 8 | standing | 0 | 0 |
| ... | 1 | fall | **1** | 0 |
| ... | 2 | fallen | 0 | **1** |
| ... | 2 | fallen | 0 | **1** |

**统计**：
- `fall_label = 1`：4,991 个 clip（8.3%）
- `fallen_label = 1`：4,498 个 clip（7.5%）

这两个比例不同是因为：一个"跌倒"瞬间（1个clip）后面通常跟着多个"倒地状态"clip。

## 6. Step 4 — ResNet18 视觉特征提取

**脚本**：[`step4_extract_features.py`](step4_extract_features.py)

### 为什么不直接让模型看视频像素？

模型直接处理原始视频帧（224×224×3 的像素值 = 150,528 个数）太"重"了。更好的做法是用一个**已经在 ImageNet 上预训练过的图像识别网络**，把每帧图像压缩成一个**512 维的特征向量**——这 512 个数字概括了这帧图像"看起来是什么样子的"。

这样，后续的时间线分割模型就不需要学习"怎么理解图像"（ResNet 已经学会了），只需要学习"怎么理解动作随时间的变化"。

### ResNet18 是什么？

ResNet18 是一个经典的图像分类网络，参数量为 1,170 万。我们用的是 torchvision 内置的版本，权重在 ImageNet 上预训练好的。

关键修改：**去掉最后的分类层**（原本输出 1000 类 ImageNet 类别的概率），保留倒数第二层（avgpool 的输出），维度正好是 **512**。

```
输入: [224×224 RGB 图像]
  ↓
ResNet18 卷积层 (17层)
  ↓
全局平均池化 (avgpool)
  ↓
输出: [512维特征向量]  ← 这就是我们需要的！
```

### 特征提取流水线

```
预解压 .mp4 文件              ffmpeg NVDEC (GPU硬解)         PyTorch CUDA (RTX 4060)
  ↓                              ↓                              ↓
读取 .mp4 字节               av1_cuvid 硬件解码 AV1       ImageNet 归一化
                                ↓                              ↓
                             scale 缩放到 224×224          ResNet18 前向传播
                             format=rgb24 转原始RGB           ↓
                                ↓                         [81帧, 512维] 特征
                             subprocess pipe → numpy
                             → torch tensor (CPU)
```

**关键变化**（相比初版 PyAV 软解）：
- 解码 + 缩放均在 GPU 端完成（NVDEC），CPU 零负担
- 不再从 tar 归档中实时读取，改为预解压 .mp4 文件直接 decode
- ffmpeg 子进程通过 `subprocess.run` 调用，pipe 传递原始 RGB 帧数据
- NVDEC 和 CUDA Core 是 GPU 内独立硬件单元，互不抢占

### Clip 特征聚合

81 帧 → 每帧一个 512 维特征 → reshape 成 [5 个 clip, 每 clip 16 帧, 512 维] → 对每 clip 内 16 帧取**平均值** → 得到 **[5, 512]**

```
81 帧特征:  ████████ ████████ ████████ ████████ ████████ █  (丢弃最后1帧)
               ↓        ↓        ↓        ↓        ↓
            clip 0   clip 1   clip 2   clip 3   clip 4
           [16,512] [16,512] [16,512] [16,512] [16,512]
               ↓        ↓        ↓        ↓        ↓
           mean()   mean()   mean()   mean()   mean()
               ↓        ↓        ↓        ↓        ↓
            512维    512维    512维    512维    512维
                      
最终: [5, 512] 特征矩阵
```

### 输出：`data/features/` 目录

```
data/features/
├── fall/
│   ├── fall_ch_001.pt
│   ├── fall_ch_002.pt
│   └── ...              ← 共 12,000 个 .pt 文件
├── standing/
└── ...
```

**每个 `.pt` 文件内部结构**：

```python
{
    "features":     torch.Size([5, 512]),   # float32, 5个clip的特征向量
    "labels":       torch.Size([5]),        # int64, 16类动作标签
    "fall_label":   torch.Size([5]),        # int64, 是否跌倒
    "fallen_label": torch.Size([5]),        # int64, 是否倒地状态
}
```

## 8. 工程优化：从软解到 NVDEC 硬件解码

### 初版问题

初版 Step 4 采用 PyAV + CPU 软件解码 AV1：
```
→ tar 读取 → PyAV 软解 → cv2 缩放 → torch tensor → GPU 推理 → ...
```

实际情况：
- CPU 解码一个视频：~650ms（tar 读取 + AV1 软件解码 + 缩放）
- GPU 推理一个视频：~2ms

**GPU 利用率仅 0.3%**，99.7% 的时间 GPU 在等 CPU 喂数据。

### 中间版：CPU/GPU 流水线并行

用 `ThreadPoolExecutor`（8 线程）并行解码 + 批量 GPU 推理，将吞吐从 **1.2 vids/s 提升到 4 vids/s（3.3×）**，12,000 视频从 ~2.7 小时降至 **50 分钟**。但瓶颈仍在 CPU 侧 AV1 软件解码。

### 最终版：NVDEC 硬件解码

RTX 4060 自带 **NVDEC**（视频硬件解码单元），支持 AV1 硬解。NVDEC 和 CUDA Core 是 GPU 内**独立硬件单元**，互不抢占资源。

方案：**ffmpeg + av1_cuvid 解码器** 替代 PyAV 软解，解码和缩放全程在 GPU 端完成，CPU 仅负责少量调度和 tensor 转换。

```
预解压 .mp4 文件          ffmpeg NVDEC (GPU硬解)        PyTorch CUDA
      ↓                    ↓                              ↓
  读取文件字节        av1_cuvid 解码 + 缩放            ResNet18 推理
  (CPU，轻量)         (全 GPU 端，CPU 零负担)          (CUDA Core)
                             ↓
                    subprocess pipe 传回
                    numpy → torch tensor
```

三个关键改动：

1. **硬件解码**：`ffmpeg -hwaccel cuda -c:v av1_cuvid`，AV1 解码从 CPU 迁移到 NVDEC，解码+缩放一步完成。

2. **预解压 mp4**：视频从 tar 归档中预先解压到 `extracted/` 目录，避免运行时 tar seek 开销和线程锁竞争。

3. **子进程并行**：8 个 `ffmpeg` 子进程通过 `ThreadPoolExecutor` 并行运行，各自通过 `subprocess.run` pipe 传回 RGB raw frames。

### 优化效果对比

| 指标 | 初版（串行软解） | 中间版（流水线软解） | 最终版（NVDEC 硬解） |
|------|:---:|:---:|:---:|
| 解码器 | PyAV CPU | PyAV CPU | NVDEC GPU |
| 吞吐 | 1.2 vids/s | 4 vids/s | **5 vids/s** |
| 12,000 视频耗时 | ~2.7h | ~50min | **~44 min** |
| GPU 利用率 | 0.3% | 有所改善 | **CUDA + NVDEC 并行 (GPU batch=12, 8 workers)** |
| CPU 负载 | 极高（AV1 软解） | 极高（AV1 软解） | 极低（仅调度） |

> NVDEC 硬解解决了 AV1 软件解码的高 CPU 开销问题。RTX 4060 的 NVDEC 和 CUDA Core 独立运作，解码不抢占推理算力。

### 目录关系

所有脚本位于 `preprocessing/`，通过 `parent.parent` 引用上一级（项目根目录）的资源：

```
KPDT0507/                       ← 项目根
├── DATASET-omnifall/           ← 数据集
│   ├── labels/                 ← 原始标注
│   ├── splits/                 ← train/val/test 划分
│   └── data_files/
│       ├── omnifall-synthetic_av1.tar  ← 原始视频归档
│       └── extracted/          ← 预解压 .mp4（Step 4 输入）
├── data/
│   ├── ofsyn_clips.csv         ← Step 2-3 产出
│   └── features/               ← Step 4 产出（12,000 .pt）
└── preprocessing/              ← 本归档文件夹
    ├── 数据预处理流程说明.md
    ├── step1_load_ofsyn.py
    ├── step2_clip_segmentation.py
    ├── step3_binary_labels.py
    ├── step4_extract_features.py
    └── verify_pipeline.py
```

各脚本中的路径配置（以 step4 为例）：

```python
OMNIFALL_ROOT  = Path(__file__).resolve().parent.parent / "DATASET-omnifall"
EXTRACTED_ROOT = OMNIFALL_ROOT / "data_files" / "extracted"
CLIPS_CSV      = Path(__file__).resolve().parent.parent / "data" / "ofsyn_clips.csv"
OUTPUT_DIR     = Path(__file__).resolve().parent.parent / "data" / "features"
```
